================================================================================
FORGE User Onboarding: Action Plans for Automated Config Generation
================================================================================
Date: 2026-04-13
Author: Luis Enrique Solano / Claude

PROBLEM STATEMENT
-----------------
FORGE's main.nf is universal -- all dataset variation lives in nextflow.config.
Users must set ~8 required params and ~15 species-specific reference paths.
Species choice (human/mouse) mechanically determines those 15 paths, yet users
currently copy-paste them from examples, risking mismatches that fail silently
or after hours of compute. The manifest CSV (8 columns) is already standardized.

The question: what is the best way to streamline config creation for new users?

CURRENT STATE
-------------
- main.nf: Universal across all 4 active workflows (AD mouse 10x, BD brain,
  BD kidney, PBMC human 10x). No per-dataset modifications needed.
- nextflow.config: Root file has all defaults. Dataset configs in
  configs/datasets/*.config override species/tissue-specific values.
- example_template.config: Exists (268 lines), well-commented, but still
  requires manual entry of 15+ reference paths.
- Reference files: Organized under /dfs7/swaruplab/lesolano/ref/ with
  predictable structure (Gencode_GRCh38/, Gencode_GRCm38/, scenic_plus_resources/,
  scATAnno_PBMC/, scATAnno_mouse_brain/, etc.)

SHARED OBSERVATIONS
-------------------
Species-derived paths (deterministic given species + genome build):
  - gtf_human_full / gtf_mouse_full
  - blacklist_bed (hg38 or mm10)
  - pycistopic.species, .blacklist_bed, .gtf
  - scenicplus.ctx_rankings, .ctx_scores, .motif_annotations, .gtf, .fai
  - scprinter.genome, .pfms
  - cicero.gtf_full, .gtf_plot
  - atac.cisbp_human / .cisbp_mouse

Tissue-derived choices (simple lookup):
  - celltypist.model (brain vs immune vs PBMC models)
  - atac.tissue_type, .initial_min_tsse
  - scatanno.reference_atlas, .atlas_name
  - QC thresholds: min_genes, mt_threshold

True user decisions (cannot be auto-resolved):
  - species, tissue_type, genome_build
  - manifest path, output directory
  - resource_tier (small/medium/large)
  - CellBender expected_cells / total_droplets
  - Whether to run differential analysis (and which comparisons)
  - Optional: reference atlas for Path A, target genes, batch correction


================================================================================
PLAN A: Experiment CSV + Generator Script
================================================================================

CONCEPT
  Two-file input: the existing manifest.csv (per-sample) plus a new single-row
  experiment.csv (experiment-level). A Python script reads the experiment CSV,
  resolves species/tissue to reference paths, and writes a ready-to-run
  nextflow.config.

USER INPUT
  1. manifest.csv (unchanged, 8-column format)
  2. experiment.csv -- one row with these columns:

  Required columns:
    experiment_name    e.g. "ad_mm_10x"      Config filename
    species            "human" or "mouse"     Drives reference resolution
    genome_build       "GRCh38"/"GRCm38"     Selects specific genome version
    tissue_type        "brain"/"pbmc"/"kidney" Drives QC presets + annotation
    manifest_path      absolute path          Path to manifest.csv
    resource_tier      "small"/"medium"/"large"

  Optional columns:
    outdir             default: "results"
    celltypist_model   auto-selected from tissue if omitted
    expected_cells     CellBender; default: 5000
    total_droplets     CellBender; default: 20000
    reference_atlas    Path A atlas dir; null = Path B
    scatanno_atlas     scATAnno reference h5ad; auto from tissue if known
    run_differential   "true"/"false"; default: false
    control_condition  required if run_differential=true
    treatment_condition required if run_differential=true
    target_genes       comma-separated gene list
    batch_correction   "none"/"mnn"; default: "none"

WHAT GETS GENERATED
  - configs/datasets/<experiment_name>.config

SPECIES RESOLUTION
  The script contains a reference registry (JSON or Python dict) mapping
  (species, genome_build) -> all 15+ paths. Adding a new genome is one entry.

IMPLEMENTATION EFFORT
  - bin/generate_config.py              ~300 lines
  - configs/reference_registry.json     ~50 lines (species -> paths)
  - configs/tissue_presets.json         ~30 lines (tissue -> thresholds/models)

PROS
  + Minimum user input: 6 required fields
  + Impossible to get species-reference mismatches
  + CSV is auditable and version-controllable
  + Same CSV always generates same config (reproducible)

CONS
  - Flat CSV is awkward for optional/nested params (differential, batch maps)
  - Cannot express arbitrary overrides without extra columns
  - Must maintain registry JSON alongside actual reference files
  - Power users may want to edit config directly anyway


================================================================================
PLAN B: Annotated Template + Validation Script
================================================================================

CONCEPT
  Keep the existing template-based workflow but add a validation script that
  catches errors before pipeline launch. Slim down the template to focus on
  true decision points. No auto-generation -- users edit manually.

USER INPUT
  1. Copy example_template.config -> my_dataset.config
  2. Fill in ~8 REQUIRED fields (clearly marked)
  3. Run: python bin/validate_config.py my_dataset.config

WHAT GETS GENERATED
  Nothing. User manually fills the template. Validation script produces a
  pass/fail report with actionable error messages.

TEMPLATE IMPROVEMENTS
  - Add species-specific reference blocks as copy-pasteable presets:
      // === HUMAN REFERENCES (uncomment if species = 'human') ===
      // gtf_human_full = '/dfs7/.../gencode.v38.annotation.gtf'
      // blacklist_bed  = '/dfs7/.../hg38-blacklist.v2.bed.gz'
      // ... (all 15 paths)
      //
      // === MOUSE REFERENCES (uncomment if species = 'mouse') ===
      // gtf_mouse_full = '/dfs7/.../gencode.vM10.annotation.gtf'
      // ...
  - Add tissue QC preset blocks similarly

VALIDATION CHECKS
  - All REQUIRED params are non-null
  - Species/reference path consistency (human + mouse GTF = error)
  - Manifest CSV exists and has correct 8 columns
  - All referenced files exist on disk (GTFs, atlases, blacklists)
  - CellBender: expected_cells < total_droplets
  - Differential: if enabled, comparisons must be non-empty

IMPLEMENTATION EFFORT
  - Rewrite example_template.config with species presets   ~80 lines
  - bin/validate_config.py                                 ~200 lines
    (uses `nextflow config -flat` to extract resolved params, then checks)

PROS
  + Zero new concepts for Nextflow users
  + Full control: every param is directly editable
  + Lowest implementation effort
  + Validation script alone is high-value

CONS
  - Users still manually handle 15+ reference paths (copy-paste from presets)
  - Template can feel overwhelming even when well-organized
  - No structured input format for programmatic tracking
  - Doesn't eliminate the core copy-paste error source


================================================================================
PLAN C: Experiment YAML + Generator + Validation (Hybrid)
================================================================================

CONCEPT
  Combine the best of A and B. Users write a ~10-line YAML file with their
  true decisions. A single script resolves species/tissue, generates the
  config, validates everything, and optionally creates a launch script.
  The template remains available as an escape hatch for power users.

USER INPUT
  A file like experiments/my_experiment.yaml:

    # FORGE Experiment Specification
    experiment_name: ad_mm_10x
    species: mouse
    genome_build: GRCm38
    tissue_type: brain
    manifest: /path/to/manifest.csv
    resource_tier: medium

    # Optional
    cellbender:
      expected_cells: 8000
      total_droplets: 25000

    reference_atlas: /path/to/ALLEN_mouse    # omit for Path B

    differential:
      enabled: true
      control: WT
      treatment: TG

    target_genes: [Trem2, Apoe, Cd33]

    # Power-user escape hatch: override any default param
    overrides:
      mofa.n_factors: 30
      atac.batch_correction: mnn

WORKFLOW (single command)
  python bin/forge_init.py experiments/my_experiment.yaml

  Output:
    VALIDATED: manifest has 8 columns, 6 samples found
    VALIDATED: all reference files exist for mouse/GRCm38
    GENERATED: configs/datasets/ad_mm_10x.config
    GENERATED: launch_ad_mm_10x.sh

    To run:  sbatch launch_ad_mm_10x.sh
    To test: nextflow run main.nf -c configs/datasets/ad_mm_10x.config -preview

WHAT GETS GENERATED
  - configs/datasets/<experiment_name>.config  (complete Nextflow config)
  - launch_<experiment_name>.sh                (SLURM submission script)
  - Validation report to stdout

SPECIES/TISSUE RESOLUTION
  Same registry approach as Plan A. Reference registry JSON maps
  (species, genome_build) -> all paths. Tissue presets JSON maps
  tissue -> QC thresholds, CellTypist model, scATAnno atlas.

IMPLEMENTATION EFFORT
  - bin/forge_init.py                    ~400-500 lines
  - configs/reference_registry.json      ~50 lines
  - configs/tissue_presets.json          ~30 lines
  - experiments/example.yaml             ~30 lines (documented example)
  - existing example_template.config remains as power-user escape hatch

PROS
  + Extremely low friction: 6-10 lines for a basic experiment
  + YAML handles optional nested params cleanly (differential, cellbender)
  + overrides: key covers 100% of edge cases
  + Built-in validation catches errors before compute
  + Generates both config AND launch script
  + YAML is human-readable, diff-friendly, version-controllable
  + Backward compatible: existing template workflow still works

CONS
  - Slightly more implementation effort than Plan B
  - Adds PyYAML dependency on login node (likely already available)
  - Three artifacts to maintain: registry JSON, tissue presets, generator script
  - Users must learn YAML format (though simpler than Nextflow config syntax)


================================================================================
RECOMMENDATION
================================================================================

Plan C (Hybrid YAML) is the strongest option because:

1. It solves the actual problem: the 15+ species-specific paths that are
   mechanically derived but currently copy-pasted.

2. The overrides: escape hatch means it handles 100% of cases.

3. Built-in validation prevents the most expensive class of error: bad
   reference paths discovered after hours of SLURM compute.

4. Implementation is incremental: start with species resolution, add tissue
   presets, add validation, add launch script generation.

Plan B (template + validation) is a good stepping stone -- the validation
script alone is high-value and could be built first, then Plan C layered on.

Plan A (CSV) works but is awkward for optional/nested params. A flat CSV
cannot cleanly express differential.control=WT or overrides without many
sparse columns.

Users must assemble references from several categories before running FORGE.
Below is a complete inventory of what is needed, where to get it, and what
preprocessing is required — organized by reference class.

Evidence base: configs from all 4 active workflows:
  AD_Mm_10X_r5     mouse / mm10 / GRCm38 / brain
  Brain_Mm_BD_r5   mouse / mm39 / GRCm39 / brain
  Kidney_Mm_BD_r5  mouse / mm39 / GRCm39 / kidney

CLASS 1: Genome Annotations (GTF + FASTA + FAI)
--------------------------------------------------------------------------------

WHAT:
  - Gencode GTF gene annotation
  - Genome FASTA (for scPRINTER, SCENIC+ chromsizes)
  - FASTA index (.fai)

WHERE TO DOWNLOAD:
  https://www.gencodegenes.org/human/  (human: GRCh38/hg38)
  https://www.gencodegenes.org/mouse/  (mouse: GRCm38/mm10 or GRCm39/mm39)

CURRENT FILES ON DISK:
  Human (hg38):
    GTF:   /ref/Gencode_GRCh38/gencode.v38.annotation.gtf
    FASTA: /ref/Gencode_GRCh38/GRCh38_FaGFF3/hg38.fa
    FAI:   /ref/Gencode_GRCh38/GRCh38_FaGFF3/hg38.fa.fai

  Mouse (mm10):
    GTF:   /ref/Gencode_GRCm38/gencode.vM10.annotation.gtf
    FASTA: /ref/Gencode_GRCm38/GRCm38.primary_assembly.genome.fa
    FAI:   /ref/Gencode_GRCm38/GRCm38.primary_assembly.genome.fa.fai

  Mouse (mm39):
    GTF:   /ref/Gencode_GRCm39/gencode.vM37.annotation.gtf
    FAI:   /ref/Gencode_GRCm39/GRCm39.primary_assembly.genome.fa.fai

PARAMS THAT USE THESE:
  gtf_human_full / gtf_mouse_full
  scenicplus.gtf, scenicplus.fai
  pycistopic.gtf
  cicero.gtf_full, cicero.gtf_plot
  scprinter.gtf_human, scprinter.gtf_mouse

PAIN POINTS:
  - GTF version must match the genome build used for alignment (Cell Ranger).
    No runtime validation exists — mismatch silently corrupts all coordinate-
    based analyses. (Priority list B1)
  - Multiple modules accept the same GTF independently (scenicplus.gtf,
    pycistopic.gtf, cicero.gtf_full, etc.) — easy to set inconsistently.
    A generator script should resolve these from a single species/build choice.

CLASS 3: CellTypist Models (RNA cell type annotation)
--------------------------------------------------------------------------------

WHAT:
  Pre-trained logistic regression classifiers (.pkl) for RNA-based cell type
  annotation.

WHERE TO DOWNLOAD:
  Auto-downloaded at runtime by the CellTypist package.
  Model catalog: https://www.celltypist.org/models

CURRENT MODELS IN USE:
  AD brain (mouse):       Mouse_Whole_Brain.pkl
  Brain_BD (human brain): Pan_Fetal_Human.pkl
  Kidney_BD (mouse):      Immune_All_Low.pkl
  PBMC (human):           Immune_All_Low.pkl

PARAM: celltypist.model

PAIN POINTS:
  - Model selection is tissue-dependent — no single model works well for all
    tissues. Users must browse the CellTypist catalog and choose appropriately.
  - Auto-download requires internet on compute nodes (not always available on
    HPC). Container pre-caching may be needed.
  - Model names are not self-documenting (e.g., "Pan_Fetal_Human.pkl" for
    aged brain tissue).
  - Kidney currently uses Immune_All_Low.pkl (immune-focused), which may miss
    kidney-specific epithelial cell types — tissue-matched model would be better
    but may not exist.

CLASS 4: scVI/scANVI Reference Atlases (RNA integration, Path A)
--------------------------------------------------------------------------------

WHAT:
  Large reference scRNA-seq datasets (h5ad) for semi-supervised cell type
  transfer via scANVI. OPTIONAL — pipeline falls back to CellTypist-only
  (Path B) when not provided.

WHERE TO DOWNLOAD:
  SEA-AD (human brain):
    https://portal.brain-map.org/explore/seattle-alzheimers-disease
    File: SEAAD_MTG_RNAseq_final-nuclei.2024-02-13.h5ad (~36 GB)

  Allen Mouse Brain Atlas (mouse brain):
    https://portal.brain-map.org/
    File: AllenRef_mouse10xv2.h5ad (~146 GB)

  For other tissues: Users must find or build their own reference dataset.

REQUIRED h5ad FORMAT:
  - Raw counts in .X matrix
  - obs columns: cell type labels (Subclass/subclass_label), batch/donor info
  - Pipeline auto-detects column naming (Subclass vs subclass_label)
  - Subsampled to 50K cells internally by prepare_reference.py

PARAMS: ref_dir_human_integrated, ref_dir_mouse_integrated

CURRENT USAGE:
  AD_Mm_10X:  ref_dir_mouse_integrated = /ref/ALLEN_mouse  (Path A)
  Brain_BD:   null (Path B — CellTypist only)
  Kidney_BD:  null (Path B)
  PBMC:       null (Path B)

PAIN POINTS:
  - Extremely large files (36-146 GB). Download and storage are barriers.
  - Allen atlas metadata column names differ between releases (subclass vs
    subclass_label) — pipeline handles this but it's fragile.
  - No reference atlases exist for many tissues (kidney, liver, etc.) —
    users may need to build their own from public scRNA-seq data.
  - Genome build of the reference should match the query data but is not
    validated.

CLASS 5: scATAnno Reference Atlases (ATAC cell type annotation)
--------------------------------------------------------------------------------

WHAT:
  Reference ATAC peak-by-cell matrices (h5ad) for transferring cell type labels
  to query ATAC data. Used when annotation_method = 'scatanno'.

WHERE TO DOWNLOAD / BUILD:
  PBMC atlas:
    Built from 10x Genomics public PBMC multiome data.
    File: PBMC_reference_atlas_final.h5ad (2.8 GB, 39K cells x 197K peaks)

  Mouse brain atlas:
    Source: GEO GSE246791 (Zu et al. 2023, Nature — whole mouse brain)
    File: mouse_brain_reference_atlas.h5ad (2.0 GB)
    Built via: /ref/scATAnno_mouse_brain/build_reference.py
      → Loads full 2.3M-cell SnapATAC2 dataset
      → Subsamples to ~150 cells per subclass (339 subclasses)
      → Filters zero-count peaks
      → Saves as h5ad

  Mouse kidney atlas:
    Source: GEO GSE157079 (Miao et al. 2021 — mouse kidney snATAC)
    File: mouse_kidney_reference_atlas.h5ad (866 MB)
    Built via: /ref/scATAnno_mouse_kidney/build_reference.py
      → Loads MatrixMarket sparse matrix + CSV metadata
      → Filters to adult (P56) samples
      → Maps cluster IDs to cell type names
      → Saves as h5ad

REQUIRED h5ad FORMAT:
  - obs column: 'celltypes' (cell type labels)
  - var_names: peak coordinates in chr:start-end format
  - Sparse binary/count matrix in .X

PARAMS: scatanno.reference_atlas, scatanno.atlas_name

PAIN POINTS:
  - GENOME BUILD IS UNDOCUMENTED in the atlas files themselves. The mouse brain
    atlas was built from GSE246791 (likely mm10 coordinates). Brain_BD and
    Kidney_BD run with mm39 genome — potential coordinate mismatch.
  - No pre-built atlases exist for most tissues. Users must build their own
    from public snATAC-seq data — requires custom Python scripting and domain
    knowledge to select the right cell type labels.
  - Build process is non-trivial: subsampling strategy, peak filtering, and
    cell type label mapping all require manual curation.
  - The build scripts exist but are not part of the FORGE repo — they live
    only in the reference directories.

CLASS 6: SCENIC+ cisTarget Databases (GRN inference)
--------------------------------------------------------------------------------

WHAT:
  Pre-computed motif enrichment rankings and scores for genomic regions.
  These are the most storage-intensive references (~100 GB total).

WHERE TO DOWNLOAD:
  Aerts Lab resources: https://resources.aertslab.org/cistarget/databases/
  Download script: /ref/download_scenic_refs.sh

  Available builds (from Aerts Lab):
    Human:  hg38 (region-based + gene-based)
    Mouse:  mm10 (region-based + gene-based)
    Mouse:  mm39 — NOT AVAILABLE from Aerts Lab. Must be created via liftover.

CURRENT FILES:
  Human (hg38):
    Rankings: /ref/scenic_plus_resources/human/hg38_region_based.rankings.feather     (33 GB)
    Scores:   /ref/scenic_plus_resources/human/hg38_region_based.scores.feather       (13 GB)
    Gene-R:   /ref/scenic_plus_resources/human/hg38_gene_based.rankings.feather       (297 MB)
    Gene-S:   /ref/scenic_plus_resources/human/hg38_gene_based.scores.feather         (327 MB)

  Mouse (mm10):
    Rankings: /ref/scenic_plus_resources/mouse/mm10_screen_v10_clust.regions_vs_motifs.rankings.feather  (17.8 GB)
    Scores:   /ref/scenic_plus_resources/mouse/mm10_screen_v10_clust.regions_vs_motifs.scores.feather    (7.7 GB)
    Gene-R/S: mm10 gene-based feather files (227 MB / 254 MB)

  Mouse (mm39) — CREATED VIA LIFTOVER:
    Rankings: /ref/scenic_plus_resources/mouse/mm39_screen_v10_clust.regions_vs_motifs.rankings.feather  (22.5 GB)
    Scores:   /ref/scenic_plus_resources/mouse/mm39_screen_v10_clust.regions_vs_motifs.scores.feather    (10.9 GB)

PARAMS: scenicplus.ctx_rankings, scenicplus.ctx_scores

PAIN POINTS:
  *** THIS IS THE #1 USER PAIN POINT ***

  1. mm39 LIFTOVER REQUIRED: Aerts Lab only provides mm10 databases. For mm39
     data, we had to build a custom 5-step liftover pipeline:
       tools/UCSC_Liftover/
         step1: Setup Python env + download UCSC liftOver binary
         step2: Extract mm10 region coordinates from feather → BED
         step3: Run UCSC liftOver with mm10ToMm39.over.chain.gz (minMatch=0.95)
         step4: Rebuild feather files with mm39 coordinates (rebuild_feather.py)
         step5: Verify output integrity
     This process drops ~0.1% of regions (unmapped or split during liftover).
     Users on mm39 must either:
       a) Repeat this liftover process, OR
       b) Use mm10 databases with mm39 data (coordinate mismatch — BAD)

  2. KIDNEY CONFIG BUG: Kidney_Mm_BD_r5 currently uses mm39 genome build but
     mm10 SCENIC+ databases — this is an active coordinate mismatch that will
     produce incorrect eRegulon predictions. Brain_BD correctly uses mm39
     databases.

  3. MASSIVE FILES: Region-based databases are 8-33 GB each. Users need ~50 GB
     per species. Download requires hours even on fast connections.

  4. NO hg19 DATABASES: Users with legacy hg19 data cannot use SCENIC+ without
     either re-aligning to hg38 or performing hg19→hg38 liftover on the ATAC
     fragments.

  5. NO mm39 GENE-BASED DATABASES: Only region-based were lifted over. Gene-
     based databases remain mm10-only. If a future module needs gene-based mm39
     rankings, another liftover round is needed.

CLASS 7: SCENIC+ Motif Annotations Table
--------------------------------------------------------------------------------

WHAT:
  Motif-to-transcription-factor mapping table (.tbl). Links cisTarget motif IDs
  to gene names for eRegulon construction.

WHERE TO DOWNLOAD:
  https://resources.aertslab.org/cistarget/motif2tf/

CURRENT FILES:
  USED:   /ref/scenic_plus_resources/motifs-v10nr_clust-nr.hgnc-m0.001-o0.0.tbl  (95 MB)
  FAILED: /ref/scenic_plus_resources/motifs-v10-nr.hgnc-m0.00001-o0.0.tbl        (0 bytes!)
  MISSING: motifs-v10-nr.mgi-m0.00001-o0.0.tbl (mouse MGI gene names — never downloaded)

PARAM: scenicplus.motif_annotations

PAIN POINTS:
  1. DOWNLOAD SCRIPT IS WRONG: download_scenic_refs.sh downloads
     motifs-v10-nr.hgnc (original, unclustered) but the pipeline actually uses
     motifs-v10nr_clust-nr.hgnc (clustered, non-redundant). The downloaded file
     is 0 bytes (failed).

  2. ALL CONFIGS USE HUMAN (HGNC) GENE NAMES: Even mouse datasets (AD, Brain,
     Kidney) use the HGNC motif table. This works because SCENIC+ internally
     maps motif IDs → TF names, and motif IDs are species-agnostic. However,
     the TF gene names in the output will be human gene symbols (e.g., SPI1
     instead of Spi1), which is confusing for mouse analyses.

  3. MOUSE MGI TABLE MISSING: The mouse-specific MGI motif annotations file
     was never successfully downloaded. This means mouse analyses cannot use
     proper mouse gene nomenclature in eRegulon output.

  4. MULTIPLE VERSIONS WITH DIFFERENT THRESHOLDS: The Aerts Lab provides files
     at different NES thresholds (m0.001 vs m0.00001). Users must choose the
     right one — no guidance exists in the pipeline.

================================================================================
APPENDIX D: Liftover Workflow for SCENIC+ Databases (mm10 → mm39)
================================================================================

When Aerts Lab does not provide cisTarget databases for the user's genome
build, a coordinate liftover is required. This was done for mm10→mm39 and
the workflow is documented at: tools/UCSC_Liftover/

STEP 1: Setup
  - Install PyArrow in a Python environment
  - Download UCSC liftOver binary (Linux x86_64)
  - Download chain file: mm10ToMm39.over.chain.gz from UCSC

STEP 2: Extract BED from feather
  - extract_bed.py reads feather column names (chr:start-end format)
  - Outputs BED4 with original region name in 4th column for mapping back
  - Memory-efficient: reads schema only, not full data

STEP 3: Run UCSC liftOver
  - liftOver mm10_regions.bed mm10ToMm39.over.chain.gz mm39_regions.bed unmapped.bed
  - Use -minMatch=0.95 (require 95% of bases to map)
  - Typical result: >99.9% mapping rate, ~50 regions unmapped/split

STEP 4: Rebuild feather
  - rebuild_feather.py reads mapping, renames columns, drops unmapped regions
  - Handles split regions (1:N mappings → dropped) and duplicate targets
  - Sorts columns by genomic coordinate
  - Writes with LZ4 compression
  - Must be run for BOTH rankings and scores feather files

STEP 5: Verify
  - verify_feather.py checks column count, coordinate format, data integrity
  - Compare region counts: expect ~0.1% loss from unmapped/split regions

RESOURCES NEEDED:
  - ~64 GB RAM (rankings feather is loaded into memory for column renaming)
  - ~1 hour wall time on a standard compute node
  - ~35 GB temporary disk for intermediate BED files

CHAIN FILES FOR OTHER BUILDS:
  hg19→hg38: hg19ToHg38.over.chain.gz
  mm10→mm39: mm10ToMm39.over.chain.gz
  mm39→mm10: mm39ToMm10.over.chain.gz
  All from: https://hgdownload.cse.ucsc.edu/goldenpath/<build>/liftOver/

ADAPTING FOR OTHER LIFTOVER TARGETS:
  The same 5-step pipeline works for any genome build conversion. Replace the
  chain file and input feather paths. The extract/rebuild scripts are genome-
  agnostic — they only care about chr:start-end column naming.
